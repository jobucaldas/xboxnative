## x86e — M0 source audit, 2026-10-26

Started clean on lane/x86e at 75b719bc. Read REBUILD.md, inherited notes,
X86-32BIT-PLAN.md and WINE-BASE-REPORT.md. Native compatibility-mode option
remains excluded; no selector transitions, JIT, Steam or graphics work planned.

Corrections from the actual fork:
- decoder.cpp:DecodeGrp4_8 accepts only FE 38 01, sets pfn=onExitSignal;
  other callback indices decode Invalid. KMemoryData::addCallback likewise
  panics for every callback except onExitSignal. A new standalone adapter must
  deliberately supply a trap; no existing arbitrary callback registry exists.
- NormalCPU is not a standalone library. boxedwine.h includes kernel, files,
  scheduler, process and thread interfaces. NormalCPU::getOp/run, CPU segment
  and exception paths, and memory code depend on them. CPU tests instantiate
  KProcess/KMemory/KThread; that proves execution without Linux guest userland,
  not absence of host-side Linux-kernel-model dependencies.
- Wine .spec ptr/long metadata does not describe buffer lengths, direction,
  ownership, handle translation or return type. Generated stack layouts can
  drive explicitly implemented M0 APIs; they cannot safely generate arbitrary
  direct calls into x64 mlp routes.
- M0's static-CRT/mvscrt description is ambiguous: a default MinGW startup
  imports additional CRT/runtime APIs. A freestanding own i686 C fixture with
  explicit entry/main and kernel32 imports isolates the requested M0 proof.
- M0 Play evidence must label that fixture separately from Spacewar. Executing
  hello32 during Play 480 does not establish execution of Spacewar's entry.

Implementation direction: reuse the real Boxedwine decoder and selected normal
integer handlers, with an isolated bounded memory/CPU adapter. Unsupported
instructions/APIs must fail explicitly. This is a milestone subset, not a claim
that the entire normal core or any commercial game already works.
